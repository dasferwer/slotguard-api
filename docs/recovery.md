# Восстановление снимка и инвариант бронирования

Инвариант: активные интервалы одной комнаты не пересекаются. Создание брони,
событие аудита и сохранённый ответ на ключ повтора принадлежат одной транзакции.
Резервная копия должна сохранять все три записи, иначе повтор после восстановления
может создать новую операцию или потерять исходный ответ.

## Повторить

Нужны Docker Compose, Python 3.12 и uv. Команды используют отдельный стенд:

```bash
export COMPOSE_PROJECT_NAME=proof-slotguard-demo
export SLOTGUARD_PORT=18010
export BASE_URL=http://127.0.0.1:18010
uv sync --frozen --extra dev
docker compose up --build -d --wait --wait-timeout 180 api
make recovery
docker compose down -v
```

Последняя команда удаляет только данные этого демонстрационного стенда.
Скрипт отказывается работать без имени Compose-проекта с префиксом `proof-`.
До первой записи он сверяет `BASE_URL` с опубликованным портом API этого проекта.
Чужой адрес или отсутствующий API приводят к отказу без HTTP-мутаций.

## Что доказывает сценарий

1. Через HTTP создаются пользователь, комната и бронь с ключом повтора.
2. `pg_dump -Fc` сохраняет снимок; `pg_restore --exit-on-error` загружает его
   в новую пустую БД того же изолированного PostgreSQL. Исходная БД сохраняется.
3. Сравниваются все строки всех публичных таблиц, включая версии, ключи и аудит.
4. Отдельный процесс API подключается к восстановленной БД. Повтор возвращает
   прежний ответ, пересечение с новым ключом даёт 409; обе попытки не меняют снимок.
5. Соседняя бронь создаётся через восстановленный API. Прямой SQL подтверждает,
   что она есть только в восстановленной БД. Это защищает проверку от случайного
   обращения к исходному API.

В конце скрипт удаляет временный API, восстановленную БД и локальный файл backup.
Ошибка удаления контейнера не пропускает попытку удаления БД. Ошибки очистки
сообщаются отдельно, сохраняя исходную причину сбоя сценария.
JSON содержит число строк по таблицам, SHA256 backup и результаты проверок.
Локальный результат этапа D сохранён в [verification-stage-d.json](verification-stage-d.json).
Команда включена в CI; сценарий находится в [recovery_smoke.py](../scripts/recovery_smoke.py).
Три проверки безопасности запускаются после старта стенда:
`uv run pytest -q scripts/test_recovery_safety.py`.

## Границы

Это логическое восстановление внутри одного тестового PostgreSQL 17 на стенде
без параллельных записей. Утрата физического кластера, восстановление глобальных
ролей, PITR и failover здесь не проверяются. Данные после момента снимка такая
копия не сохраняет; RPO=0 и время восстановления не заявляются.

Для интервью достаточно показать JSON, запрет пересечения в БД и транзакцию
создания брони. За корректность расписания отвечает exclusion constraint,
за безопасный повтор — сохранённый ответ, восстановленный вместе с бронью.
