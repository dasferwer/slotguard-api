# Архитектура SlotGuard

## Транзакции и блокировки

Проект остаётся модульным монолитом. Маршруты отвечают за HTTP-контракт и права,
сервисы — за изменение расписания, PostgreSQL — за блокировки и ограничения.

Создание берёт транзакционную advisory-блокировку ключа `пользователь:ключ`,
проверяет сохранённый ответ и затем блокирует комнату через `FOR UPDATE`.
В одной транзакции создаются бронь, аудит и сохранённый ответ. При сбое любого
шага всё откатывается. Хеш ключа может совпасть с хешем другого ключа: это только
лишнее ожидание, поскольку запись повтора ищется по полной паре пользователя и ключа.

Перенос и отмена сначала блокируют комнату, затем перечитывают и блокируют бронь.
Такой порядок одинаков для всех изменений. Версия сравнивается после получения
блокировки, поэтому два изменения одной версии не могут затереть друг друга.
Проверка прав выполняется до блокировки; владелец и комната брони неизменяемы.

Деактивация комнаты тоже берёт её блокировку и проверяет отсутствие активных броней,
у которых время окончания ещё не наступило. Поэтому после успешной деактивации
новую бронь создать нельзя. Если первой успела бронь, деактивация вернёт `409`.
Перенос в деактивированной комнате запрещён, отмена остаётся доступной.

## Защита интервалов

Окончательное правило хранится в PostgreSQL:

```sql
EXCLUDE USING gist (
    room_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
)
WHERE (status = 'active')
```

Полуоткрытые интервалы допускают соседние брони. Ограничение работает и при записи
в обход сервисного слоя. Его нарушение превращается в `409` по имени ограничения,
а не по тексту ошибки. Обработка охватывает и `flush`, и `commit`.
Другие ошибки целостности не маскируются под конфликт расписания.

## Повторы и версии

Ключ создания обязателен и ограничен пользователем. Отпечаток рассчитывается
по нормализованным данным с приведением дат к UTC. Повтор возвращает сохранённый
снимок исходного ответа; текущая бронь может уже отличаться. Запись повтора
не удаляется автоматически. Истёкший интервал не мешает повторить успешный запрос.

Изменение требует `If-Match` с положительной целой версией в двойных кавычках.
Слабые ETag, списки и `*` не поддерживаются. Значение берётся из поля `version`
ответа `GET`; сервер не выдаёт HTTP ETag. При несовпадении ответ — `412`.

## Ошибки и диагностика

| Ситуация | Результат |
|---|---|
| Нет или истёк JWT, пользователь неактивен | `401` |
| Чужая бронь | `404` |
| Нужна роль администратора | `403` |
| Пересечение интервалов или занятая комната при деактивации | `409` |
| Ключ повтора использован с другим содержимым | `409` |
| Нет версии / устаревшая версия | `428` / `412` |
| БД недоступна, истёк тайм-аут блокировки или пула | `503`, `Retry-After: 1` |

Ожидание блокировки ограничено тремя секундами, SQL-запроса — десятью, подключения
и соединения из пула — пятью. Клиент должен повторять запросы с задержкой,
сохраняя ключ создания; `Retry-After` не гарантирует восстановление через секунду.

Сервер генерирует `X-Request-ID`. Журнал содержит метод, шаблон маршрута,
код ответа и длительность без тела запроса, JWT и параметров URL.
Healthcheck проверяет доступность БД. Сам Docker healthcheck не перезапускает
контейнер: автоматическое восстановление требует внешнего управления.

## Миграция и запуск

Ревизия `20260927_0002` добавляет версию `1` к существующим броням и таблицу
сохранённых ответов. Исходные брони и аудит сохраняются. Развёртывание несовместимо
со старыми клиентами и смешанными версиями приложения: остановите запись,
сделайте резервную копию, примените миграцию отдельным процессом и обновите API.
Откат удалит сохранённые ответы и версии; после начала работы новой версии
предпочтительна исправляющая миграция, а не откат.

Compose разделяет миграцию и API; миграции не запускаются в каждом API-процессе.
Приложение работает без root, порт привязан к loopback. Демонстрационные секреты
предназначены только для локального стенда. Scrypt проверяется в синхронном
обработчике FastAPI, который выполняется в пуле потоков.
