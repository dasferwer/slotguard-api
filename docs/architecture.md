# Архитектурные решения SlotGuard

## Границы проекта

SlotGuard реализован как модульный монолит. Для текущего объёма отдельные
микросервисы увеличили бы сложность развёртывания, но не дали бы полезной
изоляции. HTTP-слой, доменные операции и доступ к данным разделены внутри
приложения, поэтому их можно развивать независимо.

## Защита от пересекающихся броней

Проверки только в приложении недостаточно:

1. запрос A проверяет свободный интервал;
2. запрос B проверяет тот же интервал;
3. оба запроса считают комнату свободной;
4. оба записывают бронь.

SlotGuard выполняет удобную для клиента предварительную проверку, но окончательный
инвариант хранит PostgreSQL:

```sql
EXCLUDE USING gist (
    room_id WITH =,
    tstzrange(starts_at, ends_at, '[)') WITH &&
)
WHERE (status = 'active')
```

Полуоткрытый интервал `[)` разрешает соседние бронирования. Частичное условие
исключает отменённые записи, сохраняя их для аудита.

## Авторизация

- регистрация всегда создаёт роль `user`;
- роль администратора создаётся только seed-процессом;
- JWT содержит идентификатор пользователя, роль и время истечения;
- актуальный пользователь и его активность проверяются в БД для каждого запроса;
- пользователь видит только собственные бронирования;
- администратор управляет комнатами и может просматривать все бронирования.

Пароли хешируются `scrypt` со случайной солью. Хеши и секрет JWT никогда не
возвращаются API.

## Сценарии отказа

| Сценарий | Поведение |
|---|---|
| БД недоступна | `/health` и запросы завершаются ошибкой; Docker перезапускает нездоровый сервис согласно политике окружения |
| Истёк JWT | API возвращает `401` и заголовок `WWW-Authenticate: Bearer` |
| Недостаточно прав | API возвращает `403` |
| Комната не найдена | API возвращает `404` |
| Комната деактивирована | Новая бронь возвращает `409` |
| Интервал пересекается | Ранняя проверка или PostgreSQL constraint возвращают `409` |
| Повторная отмена | Операция идемпотентна и возвращает уже отменённую бронь |

## Наблюдаемость

Каждый HTTP-ответ содержит `X-Request-ID`. Если клиент передал идентификатор,
сервис сохраняет его; иначе генерирует UUID. Лог запроса содержит метод, путь,
код ответа и время выполнения. Значимые изменения дополнительно записываются в
таблицу `audit_logs` в той же транзакции, что и бизнес-операция.
